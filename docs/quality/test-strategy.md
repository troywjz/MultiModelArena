# 测试策略

## 测试目标

测试重点不是证明某个模型天然更好，而是证明评测工具本身稳定、可复现、可解释，并且不会泄露密钥。当前主流程的分数必须来自程序化规则。

## 测试分层

### 单元测试

- 配置解析。
- 密钥脱敏。
- Provider 请求构造和错误归一化。
- 评分 schema 校验。
- 个人行动领域任务结构。
- JSON 输出协议解析。
- 程序化规则评分。
- 扰动响应评分。
- 报告数据聚合。

### 集成测试

- 使用 fake provider 跑完整评测流程。
- 模拟单个模型失败，确认整体运行继续。
- 从保存的运行数据生成 HTML 报告。
- 使用 fake provider 跑 `assessment-run`，确认 4 个领域和扰动评分都进入报告。

### 浏览器检查

- 报告页面能打开。
- 总览、模型卡片、评分表和任务证据存在。
- 移动端和桌面端没有明显文本重叠。

## 最小命令

项目实现后建议提供：

```powershell
python -m pytest
python -m arena assessment-run --provider fake
python -m arena assessment-report --input runs/latest
```

## 安全检查

- 用假 API Key 运行测试，断言日志和报告不出现完整密钥。
- 保存请求摘要时不保存 `Authorization` 头。
- 报告只展示 base URL 的非敏感部分。
- 完整对话只保存在本地运行目录，不上传外部服务。

## 已知缺口

- MVP 阶段不会对真实人生决策结果做长期跟踪验证。
- 第一版只覆盖 4 个个人行动决策基准题和每题 2 个扰动。
- 自然语言语义质量只进入证据，不进入主分。
